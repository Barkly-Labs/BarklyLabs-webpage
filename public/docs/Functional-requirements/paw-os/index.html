PAW OS — Functional Requirements Specification

Document: PAW-FRS-001 Version: 0.1 Platform: Commodore 64 Processor: MOS 6510 Implementation language: C (cc65), with 6502 assembly where necessary Target environment: Original Commodore 64 and VICE emulator Project: Barkly Labs

1. Project Purpose

PAW OS is a text-based operating environment designed for the Commodore 64.

Its purpose is to provide a unified, command-driven computing experience with integrated applications, file management, disk access, sound generation, and hardware interaction.

PAW OS should make the Commodore 64 feel like a complete personal computer rather than a machine that only launches individual programs.

2. Core Design Principles

Text-first: The primary interface must be usable entirely through text.

Modular: Applications and system services should be separated into maintainable modules.

Hardware-native: Software must operate within the actual limitations of the Commodore 64.

Consistent: Commands should follow predictable syntax and behavior.

Recoverable: Applications should return control to the terminal whenever possible.

Expandable: New applications must be possible without rewriting the core environment.

Resource-conscious: Memory, processor time, and storage must be managed carefully.

Backward-compatible: Existing working features must not be removed without an intentional design decision.

3. Functional Requirements

FR-001: System Startup

The system shall:

Initialize the display.

Initialize required hardware and software modules.

Display the PAW OS startup screen.

Initialize the command interpreter.

Display the terminal prompt.

Acceptance criteria: PAW OS reaches an interactive terminal after startup without requiring user intervention.

FR-002: Command Interpreter

The system shall:

Accept keyboard input.

Parse user-entered commands.

Support command arguments.

Execute recognized commands.

Display meaningful errors for unknown commands.

Return to the prompt after command completion.

Acceptance criteria: A user can execute multiple commands consecutively without restarting PAW OS.

FR-003: Terminal

The terminal shall:

Display command output.

Display a recognizable system prompt.

Support command input.

Provide a consistent visual presentation.

Allow applications to return to the terminal.

FR-004: Help System

The system shall provide:

HELP — general help.

COMMANDS — available commands.

Command-specific usage information where available.

Acceptance criteria: A user can discover available functionality without consulting external documentation.

FR-005: Disk Management

The system shall:

Support Commodore-compatible disk devices.

Use device 8 as the default device.

Allow device selection through commands such as DISK 9.

Read disk directory listings.

Display disk status and errors.

Support compatible storage devices such as 1541, 1571, 1581 and SD2IEC where hardware and firmware permit.

FR-006: File Management

The file management subsystem shall provide:

DIR — display directory contents.

FILES — open the file manager.

TYPE — display text file contents.

LOAD — load a compatible program.

RUN — execute a loaded program.

SAVE — save supported data.

DELETE — delete a file.

RENAME — rename a file.

COPY — copy files where supported by the storage device and available memory.

The file manager shall clearly communicate unsupported operations and disk errors.

FR-007: PAW Synth

The system shall provide an integrated SID synthesizer application.

It shall:

Use the Commodore 64 SID sound chip.

Provide access to the three SID voices.

Support keyboard-based note input.

Support octave adjustment.

Provide sound and voice controls.

Allow the user to stop playback.

Return to the terminal when exited.

FR-008: Sound Services

The system shall provide reusable sound functionality.

Applications should be able to use the SID subsystem without duplicating hardware initialization code.

FR-009: PHONE and DTMF

The existing PHONE and DTMF modules shall remain part of the project.

Their existing functionality must be preserved during development of unrelated subsystems.

FR-010: Memory Management

The system shall:

Track available application memory where possible.

Avoid unnecessary memory allocations.

Detect allocation failures.

Avoid overwriting reserved hardware memory.

Release resources when applications exit where applicable.

FR-011: Application Lifecycle

Applications shall follow a consistent lifecycle:

Receive control from the terminal.

Initialize application resources.

Execute application functionality.

Release or restore application resources.

Return control to the terminal.

FR-012: Error Handling

The system shall:

Display understandable error messages.

Handle invalid commands.

Report disk communication failures.

Handle unavailable memory.

Avoid crashing the entire environment when an individual application encounters a recoverable error.

FR-013: Hardware Compatibility

The system shall target:

MOS 6510 processor.

64 KB system memory.

VIC-II display hardware.

SID sound hardware.

Commodore keyboard input.

IEC-compatible disk peripherals.

Hardware-specific functionality must be tested against real hardware or an appropriately configured emulator.

5. Command Interface Standard

Commands should follow a predictable structure:

COMMAND [ARGUMENTS]

Examples:

HELP

COMMANDS

DIR

FILES

DISK 9

TYPE README

SYNTH

Command names should be case-insensitive where practical.

Invalid arguments should produce usage instructions rather than silently failing.

6. Development and Testing Requirements

Each subsystem must have:

Defined responsibilities.

Documented public interfaces.

Build integration.

Basic functional tests.

Error-handling tests.

Hardware or emulator verification.

A feature is not considered complete merely because it compiles.

It must also demonstrate its expected behavior.

7. Initial Development Priorities

Stabilize the command interpreter.

Establish command and help standards.

Stabilize disk communication.

Complete directory and file management.

Integrate PAW Synth.

Verify application entry and exit behavior.

Test memory and hardware compatibility.

Document the complete system.

8. Definition of Done

PAW OS v0.1 is considered functionally complete when:

The system starts reliably.

The terminal accepts and executes commands.

Help and command discovery work.

Disk operations work on supported devices.

File management works within documented limitations.

PAW Synth operates through the SID.

Existing PHONE and DTMF functionality remains intact.

Applications can return to the terminal.

Recoverable errors do not unnecessarily terminate the system.

The project builds successfully using cc65.

The system has been tested in VICE.

Document status: Proposed requirements baseline. Implementation status: Individual requirements must be verified against the existing source code before being marked complete.
