Functional Requirements Document

1. Purpose

Barkly Docs SHALL analyze software projects and transform their source structure into understandable, human-readable project documentation.

The system SHALL progress beyond documenting individual files and functions.

It SHALL be capable of answering:

“What is this project, how is it structured, how do its parts relate, and what does each part appear to do?”

The source code remains authoritative.

AI-assisted interpretation MAY be used to explain project structure and intent, but SHALL NOT replace deterministic source analysis.

3. Functional Requirements

FR-001 — Project Discovery

Barkly Docs SHALL accept a project directory as its primary input.

It SHALL recursively discover relevant project files.

The discovery system SHALL identify:

source files

documentation

configuration

package manifests

build configuration

test files

static assets

generated files

Git metadata where available

FR-002 — Multi-Language Analysis

Barkly Docs SHALL support analysis of multiple programming and markup languages.

Initial target languages:

Python

JavaScript

TypeScript

Astro

HTML

CSS

Markdown

Additional languages MAY be added through the same adapter architecture.

4. Language Adapter Architecture

FR-003 — Language Adapters

Each supported language SHALL have a dedicated reader/adapter.

16. Evidence-Based Interpretation

FR-017 — Source Authority

Generated explanations SHALL be traceable to discovered project evidence whenever practical.

Barkly Docs SHOULD be able to indicate:

Observed:

src/components/SEO.astro imports...

Observed:

src/pages/index.astro references...

Inferred:

These components appear to form the site's metadata system.

The system SHALL avoid presenting uncertain interpretation as confirmed source fact.

18. Project Knowledge

FR-019 — Project-Level Explanation

Barkly Docs SHOULD produce a higher-level explanation such as:

WHAT IS THIS?

HOW IS IT STRUCTURED?

WHAT ARE THE IMPORTANT PARTS?

HOW DO THEY CONNECT?

HOW DOES DATA MOVE THROUGH IT?

HOW IS IT BUILT?

HOW IS IT TESTED?

HOW IS IT DEPLOYED?

WHAT APPEARS TO BE INCOMPLETE?

This is the difference between:

“Here are 83 functions.”

and:

“Here is how this system works.”

22. Resource Requirements

FR-022 — Resource Independence

Barkly Docs SHALL prioritize lightweight deterministic processing.

The system SHOULD operate on ordinary consumer hardware for source analysis.

Large language models SHALL NOT be required for:

file discovery

syntax analysis

project structure

dependency extraction

route discovery

import analysis

documentation generation

basic project summaries

This keeps Barkly Docs useful even when CYN-X cannot run a sufficiently large model locally.

24. Testing

FR-024 — Parser Regression Tests

Every language reader SHALL have representative fixtures.

Example:

tests/

├── python/

├── javascript/

├── typescript/

├── astro/

├── html/

├── css/

└── markdown/

Tests SHALL verify that known source structures produce the expected Project Model objects.

This is especially important for CYN-X regression: Barkly Docs should have its own regression suite and shouldn't depend on CYN-X behaving correctly.

25. Failure Isolation

FR-025 — Reader Failure Isolation

A malformed or unsupported file SHALL NOT cause the entire project analysis to fail when practical.

Instead:

Project

├── Python ✓

├── JavaScript ✓

├── TypeScript ✓

├── Astro ✓

├── CSS ✓

├── Markdown ✓

└── Unknown file ⚠

Barkly Docs SHOULD report the problem and continue analyzing the remaining project.

26. Human-Centered Output

FR-026 — Understandability

Generated documentation SHALL prioritize human understanding over maximum information density.

The system SHALL prefer:

Show the shape first.

Reveal the details when the human asks.

This aligns directly with Barkly's existing human-centered philosophy: the website itself describes complex systems as something people should be able to understand, question, modify, and build upon.

27. The Actual Goal

And this is the part I really want us to put near the top of the repo:

Barkly Docs is not merely a code documentation generator.

It is a project understanding system.

The documentation generator is the first layer.

The seven language readers are the input layer.

The Barkly Project Model is the foundation.

The relationship graph is how Barkly understands structure.

The optional CYN-X layer helps turn that structure into richer human explanations.

And the website becomes the place where humans actually explore what the machine discovered.

21. Automated Document Ingestion

FR-022 — Document Source Discovery

Barkly Docs SHOULD support approved external document sources in addition to local project directories.

Initial source types MAY include:

Google Drive

Network-attached storage (NAS)

Local document directories

Additional document sources MAY be added through the same adapter architecture used by language readers.

FR-023 — Document Retrieval

Barkly Docs SHALL retrieve documents from configured sources without modifying or destroying the original source document.

The system SHALL preserve source identity and, where available:

source location

filename

document type

author information

creation and modification timestamps

source version information

FR-024 — Change Detection

Barkly Docs SHOULD detect new, modified, and unchanged source documents.

Unchanged documents SHOULD NOT be unnecessarily reprocessed.

The system SHOULD maintain sufficient source metadata to determine whether a document requires processing.

FR-025 — Document Extraction

Barkly Docs SHALL extract usable content from supported document formats.

Initial target formats MAY include:

PDF

DOCX

Markdown

TXT

HTML

Additional formats MAY be added through the same adapter architecture.

FR-026 — Document Normalization

Extracted documents SHALL be converted into a normalized Barkly document representation before publication.

The normalized representation SHOULD preserve, where available:

document title

headings

sections

paragraphs

lists

tables

links

images or image references

code blocks

metadata

The source document SHALL remain authoritative for the extracted content.

FR-027 — Document Knowledge Integration

Normalized documents SHOULD become part of the Barkly Project Model and project knowledge system.

Technical documents MAY be related to discovered project entities such as:

Projects

Components

Modules

Functions

Classes

APIs

Configuration

Tests

Deployment structures

Where relationships can be determined, Barkly Docs SHOULD represent them in the same relationship graph used for source-code analysis.

FR-029 — Source Traceability

Generated documentation SHALL remain traceable to its source document whenever practical.

The system SHOULD be able to identify which source document and source version produced a generated document.

Generated documentation SHALL NOT silently replace authoritative source material.

FR-030 — Validation and Failure Isolation

A malformed, unavailable, unsupported, or partially unreadable document SHALL NOT cause the entire document pipeline to fail when practical.

Barkly Docs SHOULD report the source, processing stage, and reason for failure while continuing with other documents.

Generated documentation SHALL NOT be published as valid documentation when required validation fails.

FR-031 — Human Review

Barkly Docs SHOULD support human review before publishing generated documentation when the source or transformation requires approval.

Human review SHOULD be configurable by source, document type, destination, or publication policy.

FR-032 — Document Publication

Validated normalized documents SHOULD be publishable to Barkly's existing documentation outputs.

Preferred flow:

Document Source

↓

Barkly Document Model

↓

JSON / Markdown / HTML

↓

Barkly Website

The website SHALL NOT need to understand every source document format directly.

Barkly Docs SHALL perform the source-specific work.

FR-033 — Human-Centered Automation

The document ingestion system SHALL prioritize reducing the work required of humans.

A human SHOULD be able to place an approved technical document into a configured source location without needing to understand the underlying ingestion, conversion, validation, or publication pipeline.

Automation SHALL remain understandable, traceable, and controllable by humans.
